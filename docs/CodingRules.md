# Coding Rules

## Translations

- English messages live in `shared/lib/i18n/locales/en.ts`, as nested objects: namespace, optional component/template/schema owner, then message keys. Calls still use dotted paths such as `t("SettingsPage.SettingsPreferences.appearance")`. In app components, import `t` from `@/lib/i18n/i18n`, under the `// LIBRARIES` comment like every other import with its group comment, never as a bare first line. Register each new language with `createTranslator(catalog)` in the `translations` map in `shared/lib/i18n/i18n.ts`; it must cover every English key. Keep `SUPPORTED_LANGUAGES` and the native supported locales in sync.
- The app's language is the user's pick in `LanguageSelector` (saved on the device), else the phone's (`getAppLanguage`). Changing it reloads the app. The app sends it as `Accept-Language` on every request and mirrors it to `user.language` on every signed-in launch.
- Server texts (emails, push) pick the language by who triggered them: during the user's own request, `parseAcceptLanguage(request header)` (`shared/lib/i18n/`), which also works before they have an account. Anything else (scheduled jobs, push, an email an admin's action sends), `getUserLanguage(user)` (`server/users/utils/`). Never hardcode English.
- Use named placeholders for dynamic text: `t("VerifyPage.codeSentDescription", { length: OTP_LENGTH, email })`. Keep complete sentences in the catalog so translations control spacing and word order. Translate text during rendering or in handlers; module-level display data stores keys, not translated strings.
- Keep a translation call on one line: `{t("OrganizationsJoinOrganizationPage.JoinOrganizationFormConfirmStep.useDifferentCode")}`, never split over three. Prettier's `printWidth: 120` (`.prettierrc`) leaves room for it; only calls with placeholders that still don't fit may wrap.
- Call `t("...")` directly where the text is used: JSX props (`label={t("SettingsPage.SettingsPreferences.appearance")}`), JSX content (`<Text>{t("SettingsPage.SettingsPreferences.language")}</Text>`), and component-local configuration or handlers. Translation calls are an exception to the rule against function calls in JSX props. Use a named constant only when the translated value is reused or participates in meaningful logic; a single translation needs no extra variable.
- Only ASCII in code strings, templates and JSX text. Lint enforces it (`no-restricted-syntax` in `eslint.config.js`); comments, `shared/lib/i18n/locales/`, seed scripts and tests are exempt. Other characters a language needs (accents, other alphabets) go in its translation. Never join pieces of text with a separator glyph, in code or in a translation: lay them out instead (see `DESIGN.md` → Separating pieces of text).
- Translate user-facing text, including labels, accessibility text, empty states, and messages. Keep identifiers, route names, and user-provided content as data.
